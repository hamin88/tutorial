## 1. Garbage Collection (GC) Mechanics## Definition
Garbage collection (GC) is an automated memory management process that clears unneeded data from a computer's heap memory. In languages like Java, Python, and JavaScript, the runtime engine looks for objects that the application can no longer reach or use, safely deleting them to free up RAM.
## Core Metrics of Memory Evaluation

* Reachability: Data is alive if it can be reached via a chain of references starting from a "GC Root" (like global variables or active thread stacks).
* Reference Counting: The engine keeps a counter of how many pointers look at an object. If that count drops to zero, the object is immediately destroyed.

## Common Garbage Collection Algorithms

   1. Mark-and-Sweep:
   * Mark phase: The collector starts at the roots and traverses all references, marking every object it hits as "alive".
      * Sweep phase: It scans the entire heap memory, deleting any objects that were not marked. Often triggers a "stop-the-world" pause.
   2. Tri-Color Marking: An advanced variant of Mark-and-Sweep used for concurrent collection to shorten pauses:
   * White set: Objects that are potential garbage candidates.
      * Grey set: Reachable objects whose own references have not been evaluated yet.
      * Black set: Reachable objects with fully evaluated references that will not be deleted.
   3. Generational Collection: Based on the empirical rule that "most objects die young," memory is split into separate zones:
   * Young Generation: Where newly allocated objects are placed. Cleaned frequently via fast "Minor GCs".
      * Old Generation: Objects that survive multiple young cleanup rounds move here. Cleaned less often via "Major GCs".

## 2. The Java Memory Model (JMM)## Definition
The Java Memory Model (JMM) is a set of specifications that dictates how threads interact through memory in a concurrent Java application [JSR-133]. It establishes the legal boundaries for compiler optimizations (like instruction reordering) and hardware cache behaviors to guarantee memory visibility and execution ordering across different processor architectures.
## The Two Core Challenges JMM Solves

   1. Visibility Problems (Caching): When a thread updates a shared variable, the new value may sit in its local CPU cache instead of flushing to main RAM instantly. Another thread running on a separate core will continue reading the stale value from its own cache.
   2. Instruction Reordering: To prevent processor stalls, the Java compiler (JIT) and the CPU reorder code statements if they think the outcome remains the same. If a secondary thread reads fields out of order, it can lead to corrupted state bugs.

## The "Happens-Before" Principle
If Action A has a happens-before relationship with Action B, the JMM guarantees that all memory updates made by Action A are completely visible to Action B, and their relative execution order is preserved.

* Program Order Rule: Within one single thread, operations happen in the exact order they are written.
* Monitor Lock Rule: Unlocking a synchronized block or lock happens-before every subsequent lock acquisition on that same monitor.
* Volatile Variable Rule: A write operation to a volatile field happens-before every subsequent read of that exact field.
* Thread Start/Join Rules: Calling Thread.start() happens-before any action inside the newly spawned thread; all actions inside a thread happens-before another thread successfully returns from a .join() call on it.

## 3. Concurrency Control: Volatile vs. Synchronized vs. AtomicInteger## The Core Difference

* volatile only guarantees visibility (threads always see the latest value).
* synchronized guarantees both visibility and mutual exclusion (locks code so only one thread runs it).
* AtomicInteger guarantees visibility and lock-free atomicity (uses hardware-level instructions for safe updates).

## Detailed Direct Comparison

| Feature | volatile | synchronized | AtomicInteger |
|---|---|---|---|
| Visibility | Yes | Yes | Yes |
| Atomicity | No | Yes | Yes (for integer operations) |
| Mechanism | Memory barriers / No caching | Monitor Locks (Heavyweight) | Non-blocking CAS (Lock-free) |
| Thread State | Never blocks | Can block / park threads | Never blocks (uses retry loops) |
| Scope | Single variables only | Code blocks or entire methods | Single integer variable only |

## Implementations## Volatile (The Visibility Flag)
Ensures that reads/writes bypass local CPU caches and prevents instruction reordering. Does not protect compound operations (like count++).

public volatile boolean keepRunning = true; 

## Synchronized (The Heavyweight Lock)
Blocks access to an entire method or code block. Only the thread holding the monitor lock can enter; others are put into a blocked state. Carries a high context-switching cost.

private int counter = 0;public synchronized void increment() {
    counter++; 
}

## AtomicInteger (The Lock-Free Alternative)
Wraps a volatile integer but utilizes a low-level CPU instruction called Compare-And-Swap (CAS) to perform compound operations atomically without blocking threads.

private AtomicInteger counter = new AtomicInteger(0);public void increment() {
    counter.incrementAndGet(); 
}

## 4. Understanding Thread Safety## Definition
Thread safety is a computer programming concept where a piece of code behaves correctly when executed by multiple threads simultaneously. It guarantees that shared data structures, variables, and logic do not become corrupted, race conditions are avoided, and the program's output matches its design specifications.
## The Three Pillars of Thread Safety

* Atomicity: Operations must execute as a single, indivisible unit.
* Visibility: Modifications made by one thread must be immediately visible to all other threads running on different CPU cores.
* Ordering: The execution sequence of instructions must be preserved or controlled so that optimizations do not expose partially initialized states.

## Common Hazards that Break Thread Safety

* Race Conditions: Occur when the correctness of a program depends on the relative timing or interleaving of threads (e.g., non-atomic count++).
* Data Races: Occur when two or more threads concurrently access the same memory location, at least one of these accesses is a write, and the threads are not using any synchronization.
* Deadlocks: A halting failure where Thread A holds Lock 1 and waits for Lock 2, while Thread B holds Lock 2 and waits for Lock 1. Both freeze indefinitely.
* Livelocks: A state where threads continuously change their states in response to each other, but make no forward progress.

## How to Achieve Thread Safety

   1. Immutability: If an object cannot be changed after it is created, it is inherently thread-safe (e.g., String).
   2. Thread Confinement: Restricting data access so that a specific piece of data can only be touched by a single thread (e.g., Local Variables, ThreadLocal).
   3. Synchronization and Locking: Enforcing mutual exclusion primitives (e.g., synchronized blocks, ReentrantLock).
   4. Lock-Free Atomic Operations: Utilizing underlying hardware CPU support like Compare-And-Swap (e.g., AtomicBoolean, AtomicReference).

## 5. The ExecutorService Framework## Definition
ExecutorService is a built-in Java framework designed to simplify asynchronous task execution and manage a pool of reusable threads. Introduced in Java 5 (java.util.concurrent), it serves as a high-level replacement for manually creating, launching, and managing individual threads.
## Core Factory Methods (Types of Pools)

* Executors.newFixedThreadPool(int n): Reuses a fixed number of threads. Excess tasks wait in a queue. Best for limiting resource usage.
* Executors.newCachedThreadPool(): Creates new threads as needed and deletes them if they sit idle for 60 seconds. Best for many short-lived, unpredictable tasks.
* Executors.newSingleThreadExecutor(): Uses exactly one worker thread to process tasks sequentially in FIFO order.
* Executors.newScheduledThreadPool(int n): A specialized sub-type (ScheduledExecutorService) that can delay task execution or run background jobs repeatedly at fixed intervals.

## Task Submission Mechanisms

* Executing a Runnable (Fire-and-Forget): Used when a task performs an isolated action and does not need to return data or throw checked exceptions.

executor.execute(() -> System.out.println("Task running asynchronously"));

* Submitting a Callable (Returns a Value): Used when the task computes a result. Instantly returns a placeholder object called a Future.

Future futureResult = executor.submit(() -> { return 42; });
Integer result = futureResult.get(); // Blocks until the worker completes the task


## Clean Shutdown Lifecycle

executor.shutdown(); // Stop accepting new tasks, finish queued onestry {
    if (!executor.awaitTermination(60, TimeUnit.SECONDS)) {
        executor.shutdownNow(); // Force quit if it takes too long
    }
} catch (InterruptedException e) {
    executor.shutdownNow();
}

## 6. Asynchronous Pipelines with CompletableFuture## Definition
CompletableFuture is an advanced Java class that represents a future asynchronous result that can be explicitly completed, chained, and combined using a functional programming style. Introduced in Java 8, it implements Future and CompletionStage to enable non-blocking asynchronous pipelines without getting trapped in "callback hell".
## Core Pipeline Stages## 1. Launching Asynchronous Tasks
By default, these use the global ForkJoinPool.commonPool() framework.

* supplyAsync(Supplier): Runs a task asynchronously and returns a value.
* runAsync(Runnable): Runs a task asynchronously but returns no value (void).

## 2. Transforming and Chaining Results (Non-blocking)

* thenApply(Function): Transforms the result of the previous stage synchronously (similar to map).
* thenAccept(Consumer): Consumes the final result with a void function.
* thenCompose(Function): Flattens nested futures if a transformation step returns another CompletableFuture (similar to flatMap).

CompletableFuture.supplyAsync(() -> "User_123")
    .thenApply(userId -> fetchUserProfile(userId))
    .thenAccept(finalOutput -> System.out.println(finalOutput));

## 3. Combining Multiple Futures

* thenCombine(): Executes two futures concurrently and runs a merging function when both finish.
* CompletableFuture.allOf() / anyOf(): Waits for either all futures to complete or the single fastest future in a group to finish.

## Understanding the "-Async" Suffix Rule

* thenApply(fn): Executes the function fn inside the same thread that just finished the previous stage.
* thenApplyAsync(fn): Forces the function fn to execute inside a separate thread grabbed from the ForkJoinPool.commonPool().
* thenApplyAsync(fn, customExecutor): Forces the function fn to run inside a separate thread managed by a custom ExecutorService pool.

## Exception Handling

* exceptionally(Function): Acts like a catch block, allowing you to intercept failures and return a safe default fallback value.
* handle(BiFunction): Always executes at the end of a stage, providing both the successful result and the error object for dual processing.

## 7. Task Modeling: Callable vs. Runnable## The Core Difference
Runnable represents a fire-and-forget task that does not return a value or throw checked exceptions, while Callable represents a task that computes a result and can natively throw checked exceptions.
## Structural Comparison

| Feature | Runnable | Callable |
|---|---|---|
| Introduced In | Java 1.0 | Java 5.0 |
| Method Name | run() | call() |
| Return Value | void | Type V (Generic type value) |
| Exception Handling | Uncaught runtime exceptions only | Can throw any checked exception |
| Execution Tool | Thread class, ExecutorService | ExecutorService only |

## Code Comparison## Runnable Implementation

Runnable runnableTask = () -> {
    try {
        Thread.sleep(1000);
        System.out.println("Runnable task completed.");
    } catch (InterruptedException e) {
        System.out.println("Interrupted!");
    }
};new Thread(runnableTask).start();

## Callable Implementation

Callable callableTask = () -> {
    Thread.sleep(1000); // Throws InterruptedException natively
    return "Callable result data";
};
ExecutorService executor = Executors.newSingleThreadExecutor();
Future future = executor.submit(callableTask);
String result = future.get();

## 8. The Stream API## Definition
The Java Stream API is a functional-style framework designed to process sequences of elements efficiently, declaratively, and often in parallel. It lets you chain pipeline operations together without mutating the underlying data source, replacing traditional nested for loops and if statements.
## The Three Structural Pillars of a Stream

   1. The Data Source: The starting point that feeds elements into the stream pipeline (e.g., Collections, Arrays, I/O channels). Streams do not store data.
   2. Intermediate Operations (Lazy Transformation): Operations that transform the stream into a different stream. They do not execute immediately; they only execute when a terminal operation is invoked.
   * filter(Predicate), map(Function), sorted(), distinct().
   3. Terminal Operations (Eager Execution): The final step that closes the stream pipeline and triggers the actual data processing loop. A stream is consumed and cannot be reused after this step.
   * collect(Collector), forEach(Consumer), reduce(), count().
   
## Declarative Pipeline Example

List names = Arrays.asList("Ana", "Peter", "John", "Victoria");

List result = names.stream()
    .filter(name -> name.length() > 4) // Intermediate stage
    .map(String::toUpperCase)          // Intermediate stage
    .collect(Collectors.toList());     // Terminal stage

## 9. Functional Interfaces## Definition
A functional interface is a Java interface that contains exactly one abstract method. Introduced in Java 8, they serve as the foundational target types for lambda expressions and method references, allowing you to treat behavior as data.
## Core Structural Rules

* Must declare exactly one unimplemented (abstract) method.
* Can include the optional @FunctionalInterface annotation to enforce compilation checks.
* Can have multiple default or static methods with full code bodies.
* Can override public methods from the Object class (like equals(Object)) without breaking the rule.

## The Big Four Built-in Interfaces## 1. Predicate
Takes one input argument and returns a boolean value (true or false).

* Method: boolean test(T t)
* Example: Predicate isLongName = name -> name.length() > 5;

## 2. Function
Takes an input argument of type T, processes it, and transforms it into a result of type R.

* Method: R apply(T t)
* Example: Function stringToLength = str -> str.length();

## 3. Consumer
Takes an input argument of type T to execute an operation, but returns nothing (void).

* Method: void accept(T t)
* Example: Consumer printer = msg -> System.out.println(msg);

## 4. Supplier
Takes absolutely no input arguments, but instantiates and returns a new object of type T.

* Method: T get()
* Example: Supplier randomNum = () -> Math.random();
